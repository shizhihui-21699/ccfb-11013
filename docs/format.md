# OTAP/OTAD 升级包格式规范 v1

本文档定义固件 OTA 升级包（`.otap`）与差分补丁流（`.otad`）的二进制格式，
以及设备端引导元数据的布局。目标是让**独立实现方**（另一家供应商、
另一门语言、另一颗 MCU）能仅凭本文档互操作。

所有多字节整数均为**小端**。所有“保留”字段必须写 0，解析时必须校验为 0；
这样未来扩展不会与旧设备的解析结果冲突。

---

## 1. 设计约束

| 约束 | 影响 |
| --- | --- |
| 设备端 RAM 有限，无法把整包读入内存 | 包头定长；签名覆盖全包但可**流式验签** |
| 只有 NOR 闪存：按扇区擦除、只能 1→0、按页编程 | 元数据用“追加记录环”，一次编程原子提交 |
| 掉电可能发生在任意一条指令 | 所有状态转换必须是“最后一步才生效” |
| 不能信任包内任何字段 | 先定界→验签→再用字段；长度都做上限与溢出检查 |
| 需要抗降级 | 单调计数器 + 单调递增的 `seq` |

---

## 2. 顶层包布局

```
偏移                      长度        内容
0                         192        包头（见 §3）
192                       manifest_len 清单（见 §4）
192+manifest_len          payload_len 载荷
192+manifest_len+payload_len 64        Ed25519 签名（见 §5）
```

- 整包必须**恰好**等于 `192 + manifest_len + payload_len + 64` 字节；
  多一字节少一字节都拒绝。严格等长让截断/拼接攻击自然失效。
- 签名覆盖 `[0, 192+manifest_len+payload_len)`，即包头、清单与载荷；
  签名本身不在被签内容内，因此无需清零占位。
- 载荷：完整包是整镜像；差分包是补丁流（§6）。
- 上限：`manifest_len ≤ 4096`，`payload_len ≤ 64 MiB`。

## 3. 包头（192 字节）

| 偏移 | 长度 | 字段 | 说明 |
| ---: | ---: | --- | --- |
| 0 | 4 | `magic` | 固定 `"OTAP"` (`4F 54 41 50`) |
| 4 | 2 | `format` | 包格式版本，v1 = `0x0001` |
| 6 | 1 | `type` | 0 = 完整包，1 = 差分包 |
| 7 | 1 | `flags` | bit0 必须装到非活动槽；bit1 差分包标志（与 type=1 必须一致）；其余位必须为 0 |
| 8 | 2 | `header_len` | 固定 192 |
| 10 | 2 | `manifest_len` | 清单字节数，1..4096 |
| 12 | 4 | `payload_len` | 载荷字节数，1..64 MiB |
| 16 | 8 | `seq` | **安全版本号**，严格递增，必须 > 设备计数器 |
| 24 | 8 | `timestamp` | Unix 秒，仅供审计，**不参与安全决策** |
| 32 | 24 | `product` | 产品标识，NUL 填充，必须含至少一个 NUL |
| 56 | 16 | `hardware` | 硬件版本标识，同上 |
| 72 | 16 | `key_id` | 签名密钥标识 = 公钥 SHA-256 的前 16 字节 |
| 88 | 16 | `nonce` | 签名者随机数，防止同内容包字节完全一致；解析时不做唯一性约束 |
| 104 | 32 | `payload_hash` | 载荷的 SHA-256 |
| 136 | 4 | `manifest_crc32` | 清单的 CRC-32/IEEE，用于快速定位损坏 |
| 140 | 52 | 保留 | 必须全 0 |

设计说明：

- **为什么 `timestamp` 不参与防回滚**：设备常常没有可信时钟。把时间当安全
  条件会制造“电池没电就被攻击”的漏洞。版本单调性只由 `seq` + 计数器保证。
- **为什么 `key_id` 单独存在**：设备可能内置多把公钥（轮换/吊销）。收到包后
  先用 `key_id` 选公钥，再验签，避免对每个密钥都做一次验签的开销；同时
  `key_id` 不匹配时立即拒绝，不泄露其它信息。
- **为什么有 `nonce`**：同一镜像重复打包（如多批次同版本）时，Ed25519 是
  确定性签名，内容相同则签名相同；`nonce` 让每个包的字节都不同，便于
  审计与去重，也避免“同包重放”在日志里难以区分。

### 3.1 版本字段

`image_version`（在清单里，见 §4）是**人类可读**版本，如 `2.3.0`。它不是
安全字段，仅用于展示与日志。防回滚只看 `seq`。二者由发布流程保证对应，
但设备**绝不**解析/比较 `image_version` 的语义。

## 4. 清单（manifest）

清单是自描述 TLV，给 MCU 用，不需要 JSON 解析器。

```
偏移  长度  内容
0     4     magic "MAN1"
4     2     version（v1 = 1）
6     2     entry_count
8     8     保留，必须 0
16    ...   条目依次排列
```

每个条目：

```
u8 tag | u16 len | len 字节数据
```

| tag | 名称 | 长度 | 必需性 |
| ---: | --- | ---: | --- |
| 0x01 | `base_hash` | 32 | 差分包必需；完整包禁止出现 |
| 0x02 | `base_seq` | 8 | 差分包必需（可为 0） |
| 0x03 | `image_version` | ≤64，不含 NUL | 必需 |
| 0x04 | `build_id` | ≤96，不含 NUL | 必需 |
| 0x05 | `rollback_floor` | 8 | 可选 |
| 0x06 | `notes` | ≤1024 | 可选 |
| 0x07 | `delta_patch_sha256` | 32 | 差分包必需，等于载荷 SHA-256 |
| 0x08 | `target_image_hash` | 32 | 差分包必需 |
| 0x09 | `target_image_size` | 8 | 差分包必需 |

解析规则（任何一条不满足即拒绝整个包）：

1. 版本必须等于 1；保留字节必须为 0。
2. 标签不得重复、不得未知；条目总长必须精确等于 `manifest_len`（不能
   有多余尾部字节）。
3. 定长字段长度必须精确匹配；字符串长度必须在上限内且不含 NUL。
4. 完整包与差分包的字段集合互斥（见表中“必需性”）。

`rollback_floor`：发布方可以声明“升到这个版本后，至少要把计数器抬到 F”。
设备在安装时校验 `seq ≥ rollback_floor`（防止包自身的版本被做低），
在 `confirm` 时执行 `counter = max(counter, seq)`。它用于紧急吊销：
例如发现 1.x 有严重漏洞，可以发布 `seq=100` 的修复包并令
`rollback_floor=100`，之后任何 `seq<100` 的包都装不进去。

## 5. 签名

- 算法：Ed25519（RFC 8032），64 字节签名，32 字节公钥。
- 私钥：32 字节 seed；工具把它与派生公钥拼成 64 字节 `seed‖pub` 存储。
- 被签内容：`header ‖ manifest ‖ payload`，即 `[0, sig_offset)`。
- 验证顺序（设备端）：
  1. 检查总长度与 `signature_offset` 一致；
  2. 检查 `key_id` 与本地公钥匹配；
  3. 校验 `manifest_crc32`（快速失败，避免对明显损坏的包做昂贵验签）；
  4. **流式**计算 `SHA-512(R ‖ A ‖ M)` 并做 Ed25519 验证；
  5. 验签通过后才解析清单、比较产品/硬件、检查 `seq`；
  6. 重新计算载荷 SHA-256 并与 `payload_hash` 比较。

第 4 步之所以可以流式：Ed25519 验签只需对消息做**一次**哈希
（`h = SHA-512(R‖A‖M)`），之后是两次标量乘法。实现里
`Ed25519Verifier` 先喂入 `R` 与公钥 `A`，再随读取边喂消息，最后 `finish()`。
服务端签名需要两遍哈希（先算 `r`，再算 `S`），但包在服务端内存里，
代价可忽略。

设备路径调用 `verify_package_streaming(pkg, pk, key_id, chunk_bytes)`，
按 `chunk_bytes` 分块喂给验签器；`verify_package()` 是同一实现、
一次性喂完的特例。两者走完全相同的检查顺序，测试用 1/17/4096/100000
字节四种分块交叉验证结果一致。

### 5.1 密钥标识

`key_id = SHA-256(public_key)[0..16)`。它是**索引**而非安全边界：真正的
信任来自验签。设备用 `key_id` 选择要用的公钥；如果包里写的是未知
`key_id`，直接按“签名无效”拒绝。

## 6. 差分补丁格式（OTAD v1）

补丁流作用在 base 镜像上，逐字节产生 target：

| 操作码 | 名称 | 参数 | 语义 |
| ---: | --- | --- | --- |
| 1 | `COPY` | varint `len` | 从 base 当前游标拷贝 `len` 字节并前进游标 |
| 2 | `SEEK` | varint `offset` | 把 base 游标设为 `offset` |
| 3 | `LITERAL` | varint `len` + `len` 字节 | 直接输出这些字节 |
| 4 | `END` | 无 | 结束 |

- `varint` 为 LEB128（每字节低 7 位数据、高位续位），最多 10 字节。
- 补丁流头部 24 字节：

| 偏移 | 长度 | 字段 |
| ---: | ---: | --- |
| 0 | 4 | magic `"OTD1"` |
| 4 | 2 | 版本 = 1 |
| 6 | 1 | 操作码版本 = 1 |
| 7 | 1 | 生成时使用的块大小 W（仅提示，应用端不需要） |
| 8 | 8 | base 镜像长度 |
| 16 | 8 | target 镜像长度 |

差分安装的额外约束：**目标槽不能是 base 所在的槽**。设备端把补丁应用在
内存里，然后写目标槽；若目标槽就是 base 槽，擦除会毁掉补丁的输入。设备会
在选择目标槽后检查并拒绝（`rejected-base-mismatch`），要求先完成一次切换
再装差分。

应用端必须校验：

1. 头部 base 长度 == 本地 base 长度；
2. target 长度 == 清单 `target_image_size`；
3. 每条 `COPY` 不越 base 边界，`LITERAL` 不越补丁边界；
4. 累计输出不得中途超过 target 长度；
5. `END` 之后不得有剩余字节，累计输出必须恰好等于 target 长度；
6. 最终输出 SHA-256 == 清单 `target_image_hash`（**这是真正的安全边界**：
   即使补丁被构造得“能跑完”，结果不对也会被拒绝）。

生成算法（`delta_create`）：在 base 上按 W 字节滑动建立 16 位哈希索引，
对 target 每个位置查表、逐字节确认，命中则输出 `COPY`（必要时先 `SEEK`），
否则进入 `LITERAL`。仅做等长匹配、不回退，实现简单、结果确定。

局限：不做“复制+增量”近似匹配，因此对完全重排的数据压缩率一般。对固件
（大段相同、局部改动）足够；实测 20 KB 镜像只改 4 处时补丁约 470 字节。

## 7. 设备端引导元数据

### 7.1 分区布局

```
[ 引导元数据区 ] [ 槽 A ] [ 槽 B ]
```

默认：元数据 8 个扇区（32 KiB，扇区 4 KiB），槽大小由产品决定，两槽等大。
`DeviceLayout::make()` 会校验“元数据 + 两槽 ≤ 闪存容量”。

### 7.2 槽内镜像布局

```
[ ImageHeader 128 字节 ] [ 镜像体 ]
```

`ImageHeader`：

| 偏移 | 长度 | 字段 |
| ---: | ---: | --- |
| 0 | 4 | magic `"OTIM"` |
| 4 | 2 | 版本 |
| 6 | 2 | 头长度 = 128 |
| 8 | 8 | `seq` |
| 16 | 8 | 镜像长度 |
| 24 | 32 | 镜像 SHA-256 |
| 56 | 32 | 版本字符串（NUL 填充） |
| 88 | 24 | product |
| 112 | 16 | hardware |
| 120 | 8 | 保留 |
| 124 | 4 | CRC-32（对前 124 字节） |

镜像头与引导记录冗余记录 `seq/hash/size`，三者不一致即视为损坏。

### 7.3 引导记录环

引导元数据区被划分为 64 条 512 字节记录（每个 4 KiB 扇区 8 条）。
每条记录是**完整状态快照**：

| 偏移 | 长度 | 字段 |
| ---: | ---: | --- |
| 0 | 4 | magic `"OTBS"` |
| 4 | 2 | 版本 |
| 6 | 2 | 记录长度 = 512 |
| 8 | 8 | `record_seq` |
| 16 | 8 | `counter`：已确认可启动的最高 `seq` |
| 24 | 1 | `active_slot` |
| 25 | 1 | `boot_attempts` |
| 26 | 6 | 保留 |
| 32 | 120 | 槽 0 元数据 |
| 152 | 120 | 槽 1 元数据 |
| 508 | 4 | CRC-32（对前 508 字节） |

槽元数据（120 字节）：`state(u8)` + 3 字节保留 + `seq(u64)` +
`image_size(u64)` + `image_hash(32)` + `version(32)` + 36 字节保留。
`state`：0 = Empty，1 = Pending，2 = Good，3 = Bad。

**提交语义**：写入新状态时，总是选**一条已擦除的记录槽**，把 512 字节
一次性编程。因此：

- 编程原子性由记录 CRC 保证：撕裂的记录 CRC 必不成立，加载时被忽略；
- 上电时扫描全部记录，取 `record_seq` 最大的**有效**记录；
- 环满时擦除整个元数据区，先把当前最新状态作为基线写回，再写新记录。

### 7.4 状态机

槽状态：`Empty → Pending → Good`，或 `Pending → Bad`。

```
选择目标槽（安装前）:
  active=Good              -> 另一槽（标准 A/B 交替）
  active!=Good, 另一槽Good -> active（覆盖试运行/损坏的那一槽）
  两槽都不是 Good          -> active（首次安装即写 0 号槽）
  ↑ 不变式：绝不覆盖当前唯一的 Good 槽，否则新镜像启动失败就没有回退镜像

安装（服务端包 -> 设备）:
  1. 擦除目标槽
  2. 写 ImageHeader
  3. 写镜像体；回读并校验 SHA-256 与头字段（差分包在此步之前已应用完补丁）
  4. 追加引导记录：target.state = Pending, active_slot = target, attempts = 0
     ↑ 只有这一步成功，设备才会尝试新镜像

上电（boot_and_select）:
  active 槽有效？
    ├─ 是，state=Good    -> 直接启动
    ├─ 是，state=Pending -> attempts += 1 并提交；
    │                      若 attempts 已达上限 -> 标记 Bad 并回退
    └─ 否               -> 标记 Bad，尝试另一槽
                              另一槽有效 -> 回退并从其启动
                              否则       -> NoBootable（进入恢复模式）

自检成功（confirm_running）:
  state = Good, attempts = 0, counter = max(counter, seq)
```

关键点：**`counter` 只在 `confirm` 后抬升**。这保证：

- 新镜像试运行失败、回退到旧槽时，旧槽的 `seq` 仍大于等于计数器，
  不会被自己的防回滚挡住；
- 安装被拒的包不会改变任何状态；
- 攻击者无法通过“刷一个高 seq 的坏包再断电”来永久锁死设备。

## 8. 解析器的硬性规则

实现方必须遵守（这也是本项目测试覆盖的内容）：

- 所有长度先做上限、再做到达性检查；所有偏移累加用溢出安全的方式。
- 在所有校验通过前，`product`/`hardware`/`seq` 等字段一律视为敌意输入。
- 拒绝：长度不符、魔数错误、版本不支持、保留位非 0、重复/未知标签、
  清单尾部多余字节、`flags` 未知位、`delta` 标志与类型不一致。
- 签名失败与格式错误分开报告（便于诊断，但对外都只是“拒绝”）。
- **绝不**用 `image_version` 做安全比较；**绝不**信任 `timestamp`。

## 9. 兼容性与扩展

- 包头保留区 52 字节、清单可新增标签、槽元数据保留 36 字节——新功能优先
  用“新标签 + 设备忽略未知可选字段”的方式演进。
- 包格式版本不匹配时**拒绝**（不尝试猜测）。向后兼容通过发布新旧两版包
  实现，而不是让设备猜。
- 若将来需要多签名（如厂商 + 客户联签），签名区可扩展为
  `u8 count | (key_id, sig)*`；`signature_offset` 的定义已把签名排除在
  被签内容外，因此无需改变现有签名范围。
